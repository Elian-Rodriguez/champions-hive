# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**Champion Hive** is a multi-sport tournament management platform (football, micro/futsal, basketball, banquitas, tejo). A FastAPI backend exposes a tournament/bracket engine; a React PWA frontend provides a public scoreboard, an admin management panel, a referee live-scoring panel and a team-captain panel. Four roles: **superadmin** (runs the platform, sells and supports), **admin** (organizer, owns their own tournaments), **referee** (loads results for assigned matches) and **captain** (sees only their own team). **Comments, identifiers, and API messages are in Spanish** — keep writing them in Spanish.

## Commands

### Backend (FastAPI, Python 3.10)

```bash
cd backend
source .venv/bin/activate                # o usa .venv/bin/python directamente
pip install -r requirements.txt
uvicorn app.main:app --reload            # http://127.0.0.1:8000
```

- API docs: `http://127.0.0.1:8000/docs`
- Default DB: SQLite at `backend/champion_hive_local.db`. Set `DATABASE_URL` to a `postgresql://...` URL to use Postgres (`psycopg2-binary` is installed).
- On startup the app runs `create_all()` + `run_sqlite_migrations()` and seeds the `.env` admin as **superadmin** (promoting it if the DB predates the role).

### Frontend (React + Vite, TypeScript)

```bash
cd frontend
npm install
npm run dev        # Vite dev server on http://localhost:5173 (CORS-allowed by the backend)
npm run build      # tsc + vite build → dist/
```

The API base URL comes from `VITE_API_URL` (see `frontend/.env.example`), defaulting to `/api/v1` for the combined nginx image. For a separate backend use `VITE_API_URL=http://127.0.0.1:8000/api/v1`.

## Architecture

### Backend (`backend/app/`)

- **`main.py`** — FastAPI app (`title="Champion Hive API"`). On startup runs `Base.metadata.create_all()` + `run_sqlite_migrations()`, installs CORS (allows `localhost:5173`/`127.0.0.1:5173`) and the slowapi rate-limiter, then mounts eight routers under `/api/v1` plus a `StaticFiles` mount at `/api/v1/media` that serves the highlight clips from disk (it hangs off `/api/v1` so the existing nginx `location /api/` and the Vite dev origin both cover it with no extra config, and it answers Range requests, which is what a `<video>` needs to seek).
- **`db/database.py`** — SQLAlchemy engine/`SessionLocal`/`get_db`. SQLite gets `check_same_thread=False`. `run_sqlite_migrations()` is an ad-hoc migration shim: it reads `PRAGMA table_info(...)` and `ALTER TABLE ... ADD COLUMN` for any model column missing from an existing SQLite table. **There is no Alembic migration history** (alembic is installed but unused — no `alembic/` dir or `alembic.ini`).
- **`db/models.py`** — all 16 ORM models + enums. Defines a custom **`GUID`** `TypeDecorator` storing UUIDs as native Postgres `UUID` or `CHAR(32)` on SQLite — this is what makes the same models run on both backends.
- **`schemas.py`** — Pydantic v2 request/response schemas (`from_attributes=True`) for every resource.
- **`core/config.py`** — pydantic-settings `Settings` loaded from `.env`: `SECRET_KEY` (defaults to the insecure `dev-insecure-key-change-in-production`), `ALGORITHM` (`HS256`), `ACCESS_TOKEN_EXPIRE_MINUTES`, `DATABASE_URL`, `LOG_LEVEL`, `APP_BASE_URL` (where the emailed link points), the `SMTP_*` block + `RESET_TOKEN_MINUTES` (see *Password recovery* below), `MEDIA_ROOT` + `MAX_VIDEO_MB` and the `CONTENTFUL_*` block (see *Best plays* below) and `TIMEZONE_OFFSET_MINUTES` (default `-300`, UTC-5) — timestamps are stored in UTC and converted client-side, but the notification texts the server writes have no device to read the zone from, so they use this offset.
- **`core/security.py`** — bcrypt hashing via passlib (`get_password_hash`/`verify_password`) and JWT via python-jose (`create_access_token`/`decode_access_token`).
- **`core/deps.py`** — auth dependencies and the **permission model**. Roles (`ROLES_VALIDOS`, labeled in `ROL_LABELS`): `superadmin` (sees/administers everything, the only one who creates organizers, assigns their quota and can `reset_all`), `admin` (organizer; owns the tournaments they create and the accounts they open), `referee` (only loads results for matches assigned to them), `captain` (only reads their own team). `require_staff` means *can administer a tournament* and is `admin`+`superadmin` — **referees and captains are not staff**. `puede_gestionar_usuario(actor, objetivo)` is the account-level ownership check: superadmin over everyone, an organizer only over themselves and the captains/referees they created (`created_by_id`). `puede_administrar(user, tournament)` is the ownership check: superadmin always, admin only for their own; a tournament with `owner_id IS NULL` is legacy (created before ownership existed) and stays editable by any admin so nothing is orphaned. 401 on bad token, 403 on wrong role or another admin's tournament.
- **`core/limiter.py`** — shared slowapi `Limiter` keyed by remote address, default `600/minute` (login is further limited to `10/minute`, asking for a recovery link to `5/hour`). That address is only the real client because uvicorn runs with `--proxy-headers --forwarded-allow-ips=127.0.0.1` (see `deploy/supervisord.conf`): behind nginx every request arrives from 127.0.0.1, so without it the limits would be shared by the whole platform instead of per visitor.
- **`core/log.py`** — the application log (`configurar_logging` + `logger`), out through stdout, which is what docker/supervisor collect. See *Audit trail* below.
- **`services/strategy.py`** — the standings engine, Strategy pattern. `StrategyFactory.get_strategy(sport_type)` returns `BasketballStrategy` (win/loss only, no draw), `TejoStrategy` (win/loss, and **the loss is worth 0** — that zero is the whole reason it is not the basketball one, where FIBA gives 1) or `FootballStrategy` (win/draw/loss; also used for `micro` and `banquitas` — see `FOOTBALL_LIKE_SPORTS`); unknown sports raise `ValueError`. `PUNTOS_POR_EVENTO` / `puntos_del_evento()` say what each loaded event adds to the score — a goal is 1, a tejo *moñona* is 9 — and the three scorer aggregations (dashboard, `player_stats`, the captain's summary) rank by **points, not by event count**. `SPORT_DEFAULTS` holds the per-discipline defaults (`points_config`, `match_duration`, `waiting_time`) that `create_tournament` fills in for fields the organizer omits. `calculate_standings(matches, sport_type, tiebreaker_rules)` accumulates per-team points/goals, derives fair-play penalties from card events, then sorts by an **ordered, configurable tiebreaker list**. **Standings are computed on the fly and never persisted.** Only **finished** matches accumulate (`cuenta_para_la_tabla`): `Match.home/away_score` default to `0`, so a freshly generated fixture is full of 0-0 `scheduled` matches that would otherwise count as draws and inflate everyone's PJ. Teams still register in the table from any match, so they show up with PJ 0 as soon as there's a fixture. Callers must therefore include `status` in each match dict — `_matches_to_dicts` does; a dict without `status` falls back to counting whenever both scores are set, which is what keeps the external payloads of `POST /matches/standings` working.
- **`api/`** — one router per domain: `auth_routes`, `team_routes`, `tournament_routes` (the largest — holds the fixture/bracket engine), `venue_routes`, `match_routes`, `notification_routes`, `captain_routes`, `highlight_routes`.
- **`services/auditoria.py`** — records who changed what, with the previous value (see *Audit trail* below).
- **`services/bracket.py`** — writes the result of a match into the crossings that depend on it, and **rewrites** them when it changes (see *Bracket propagation* below).
- **`services/correo.py`** — outgoing mail over stdlib `smtplib`; today only the recovery link. With no `SMTP_HOST` it does not send and does not fail.
- **`services/jugadas.py`** — builds a highlight's payload (resolving player, team and match label in one query instead of three per card) for the two routers that need it; it works across several tournaments at once because a captain may run teams in two, of different disciplines.
- **`services/media.py`** — files on disk (today, the highlight clips): the server picks the name, the extension decides the Content-Type and the first bytes are checked (see *Best plays* below).
- **`services/contentful.py`** — optional CDN mirror of the clips, **off by default**; stdlib `urllib`, no new dependency, same rule as `correo.py`: unconfigured means it does not upload and does not fail.
- **`services/disciplina.py`** — suspensions by accumulated cards, **off unless the organizer turns them on** (see *Suspensions* below).
- **`services/notifications.py`** — turns a match change into avisos for the captains of both teams (see *Notifications* below).
- **`services/validacion_calendario.py`** — reads the whole calendar back and reports what is crossed (see *Calendar validation* below).

### Data model (`db/models.py`)

```
Tournament ─┬─ Stage ─── Match ─┬─ MatchStat   (per-event: goals, cards…)
            │                   ├─ MatchLineup  (who actually played that match)
            │                   └─ StageSlot    (unresolved bracket positions)
            ├─ Sponsor
            ├─ TournamentPhoto
            └─ MatchHighlight   (best plays: the clip's record; the video is on disk)
Tournament ─ TournamentTeam ─ Team ─ TeamPlayer ─ Player   (M2M join tables; TournamentTeam holds group_name, approval status and the points sanction, TeamPlayer holds jersey number)
AuditLog                                                    (who changed what, with the previous value; no FKs on purpose)
PasswordResetToken ─ User                                   (recovery link: hash of the token, expiry, single use)
Venue ─ Court ─ Match                                       (a Match is played on a Court)
User ─ TeamManager ─ Team                                   (who captains which team; the captain's whole scope)
User ─ Notification                                         (inbox: reschedules, venue changes, results)
User                                                        (email, hashed_password, role, name, phone,
                                                             max_tournaments, created_by_id,
                                                             must_change_password, created_at, last_login_at)
```

Enums: **SportType** `football|micro|basketball|banquitas|tejo` · **StageType** `group|knockout|league|swiss` · **MatchStatus** `scheduled|live|finished|postponed` · **SlotType** `team|winner_of|position`.

`Tournament` carries the tournament config as JSON columns: `points_config`, `tiebreaker_rules`, `discipline_config` (see *Suspensions* below), plus `match_duration`/`waiting_time` and branding (`logo_url`/`banner_url`). `Stage` has an `order_index` (its real position in the tournament; named that way because `order` is a reserved word and `run_sqlite_migrations` emits unquoted `ALTER TABLE`) and a JSON `config` holding the per-stage rules: `team_ids` (which teams play this stage — empty means all), `double_round` (ida y vuelta), `qualifiers_per_group` and `best_thirds_count` (`"auto"` completes the bracket to a power of 2). `Match` has `home/away_team_id`, `home/away_score`, `court_id`, `bracket_round`, scheduling timestamps, `walkover` (see *Matches that are not played* below) and, for the knockout tie, `home/away_penalties` plus `tie_id`/`leg` (see *How a knockout tie is decided* below).

### Bracket / fixture engine (`api/tournament_routes.py`)

This router is the non-obvious core. Key endpoints (under `/api/v1/tournaments`):

- `POST /stages/{stage_id}/generate_fixture` — round-robin fixture per stage, assigns courts; honours `config.team_ids` and `config.double_round`; refuses to regenerate if the stage already has live/finished matches. It also refuses on a **`knockout` or `swiss`** stage, naming the route that is theirs (the Cuadro tab, `swiss_round`): those are not played round-robin, so all the call did was delete what the stage already had — in a knockout, the bracket that had just been seeded. The panel no longer paints the «Fixture» button on those rows either (`tieneFixture` next to `STAGE_TYPES` in `AdminView.tsx`); it had it on every stage, one click away.
- `PUT  /stages/{stage_id}` — rename a stage, change its type (blocked once it has live/finished matches) or update its `config`. `POST /{tournament_id}/stages/reorder` takes the ordered `stage_ids` and rewrites `order_index`.
- `GET  /stages/{stage_id}/standings_by_group` — per-group standings (`_build_group_standings`).
- `GET  /stages/{stage_id}/qualifiers` — who advances, per `config.qualifiers_per_group` + `best_thirds_count` (`_compute_qualifiers`). Single source of truth for the public "Clasificados" panel. With `"auto"` the bracket is completed to the next power of 2 **with repescados and never by shrinking**: it used to fall back to the previous power of 2 when the repescados did not reach, which silently dropped qualified teams (six group champions became a bracket of four). Now everyone who qualified stays and the payload reports the `byes` the top seeds get.
- `GET  /stages/{stage_id}/best_thirds` — ranks the teams just below the cut across groups (thirds when 2 qualify, seconds when 1): points → goal diff → goals for → goals against.
- `POST /stages/{stage_id}/advance` — reads real standings and creates next-stage matches from a `pairings` payload (`{h_group, h_pos, a_group, a_pos}`, 1-based; use group `"__all__"` for LEAGUE/SWISS).
- `POST /stages/{stage_id}/seed_bracket` — builds a full knockout tree from a `round1` crossing list, plus optional `byes` (seeds that start in round 2), `two_legged` and `third_place`. What has to be a power of 2 is the number of **teams** (`2 * len(round1) + len(byes)`), not the number of crossings: `_plan_de_cuadro` says which slots of the round-2 layer are byes and which are played, and a mismatch answers 400 naming how many of each are needed. Either side of a crossing (or a bye) can be `{"home_winner_of": "<match_id>"}` instead of a group position, which is what makes a play-in real: the winner of a match in another stage enters the bracket as one more qualifier. An optional `plan` (a `"match"`/`"bye"` per tie, **in bracket order**) says *which* tie each bye waits in; without it `_plan_de_cuadro` gives the byes to the top seeds. `_plan_pedido` validates it and only the order is the organizer's: the counts come from how many teams there are, since that is what makes the tree close. It exists because the counts alone do not identify a bracket — a hand-drawn cuadro of six passed validation and came back rearranged, with the team that was waiting in tie 1 showing up in tie 3.
- `GET  /stages/{stage_id}/bracket_tree`, `POST /stages/{stage_id}/resolve_position_slots` — bracket-tree readout and slot resolution.

**`StageSlot`** is how knockout brackets reference not-yet-known teams: a slot is a literal `TEAM`, the `WINNER_OF` a prior match, or a standings `POSITION` in a group. Slots are resolved (`_auto_resolve_winner_slots`) as upstream results land.

### Other routers (under `/api/v1`)

- **auth** (`/auth`): `register`, `login` (OAuth2 password form, `10/minute`, returns `must_change_password`), `me`, `roles`, `change_password`, `forgot_password` + `reset_password_confirm` (recovery by email, see below), `audit` (superadmin: the platform's account trail), `list_users` (scoped: superadmin sees all, an organizer only the accounts they created), `update_user` (role/estado/cupo), `reset_password` (support reset — returns a one-time temp password and forces a change on next login), `list_referees`, `delete_user`.
- **teams** (`/`): teams within a tournament, `shuffle_groups` (random group assignment), per-team group reassignment, the points sanction (`PUT /tournaments/{tid}/teams/{team_id}/points_adjustment`) and players within teams (with jersey numbers). `PUT /teams/{id}` takes **`TeamUpdate`** (every field optional) — with `TeamBase` there, changing only the uniforms or only the crest answered 422 because `name` was required.
- **venues** (`/venues`): venue + court CRUD.
- **matches** (`/matches`): `list`, `schedule`, `update_match_status` (scheduled→live→finished, plus `postponed` and the `walkover` flag), live event recording (`record_event`/`get_match_events`) plus the corrections the referee makes in the field — `PUT /matches/events/{id}` (`event_data` is **merged**, not replaced, so fixing the minute never drops the team) and `DELETE /matches/events/{id}`, both gated by the same `_asegurar_puede_dirigir` as recording — the match sheet (`GET /matches/{id}/lineup`, public, and `PUT /matches/{id}/lineup`, same scope as recording) and a stateless `POST /standings` that computes a table from a posted match list + rules. `update_match_schedule` and `update_match_status` take a `snapshot_partido` before writing and hand it to `services/notifications.py`, which is what turns a reschedule into an aviso; `update_match_status` also calls `propagar_resultado` so the bracket follows the result.
- **teams** also holds the captains of a team: `GET/POST /teams/{id}/managers` and `DELETE /teams/{id}/managers/{user_id}`. The POST is the only user creation an organizer can do — it opens a `captain` account (with a generated temp password if none is given) and links it to the team; without it a 20-team tournament would need the superadmin for every captain.
- **notifications** (`/notifications`): the authenticated user's inbox — `list`, `unread_count`, `{id}/read`, `read_all`, `delete`, plus `POST /broadcast/{tournament_id}` for the organizer's manual notice to the captains of their tournament.
- **highlights** (`/`): the best plays — `GET /tournaments/{tid}/highlights` (public, gated by the `jugadas` switch; the unpublished ones only reach the owner), `GET /tournaments/{tid}/highlight_plays` (the discipline's catalogue), the multipart `POST /tournaments/{tid}/highlights`, the `POST .../highlights/link` for a clip that already lives on YouTube, `PUT`/`DELETE /highlights/{id}` and `POST /highlights/{id}/mirror`. `GET /highlights/config` reports the size cap and whether Contentful is on — a button that answers 400 because the integration is off is worse than no button.
- **captain** (`/captain`): `teams` (teams they run, with tournament and group), `matches` (upcoming / played / live, each with rival, date, court and venue), `highlights` (the best plays of their matches — see below) and `teams/{id}/summary` (record, form, position per stage, per-player goals and cards). Every endpoint starts from `_equipos_del_usuario`: a team that isn't there is a 403.

### Ownership, roles and public visibility

`Tournament.owner_id` is the admin who created it; `GET /tournaments` returns only your own when authenticated as admin (all of them to superadmin, and all of them unauthenticated — the public scoreboard needs them). Every write path goes through `_torneo_administrable` / `_fase_administrable` in `tournament_routes.py` (and the equivalents in `team_routes.py` / `match_routes.py`). Referees write only through `_asegurar_puede_dirigir`, which requires `Match.referee_id == user.id`; `GET /auth/referees` exists so an admin can assign referees without being able to list or manage the rest of the users.

**No organizer sees another organizer's setup.** Beyond the tournaments themselves, that means: `GET /venues` filters through `sedes_visibles` (own + legacy `owner_id IS NULL`), `_canchas_disponibles` restricts every court assignment (fixture, swiss, advance, seed_bracket and the bulk calendar) to those same venues, the dashboard's venue count uses the same list, `GET /auth/users` only returns accounts with `created_by_id == me`, and `GET /auth/referees` adds the platform's referees (created by a superadmin, or legacy) but never another organizer's. The superadmin bypasses all of it on purpose — that is what makes support possible.

`Tournament.visibility` is a JSON of publish switches — `sanciones`, `nominas`, `metricas`, `jugadas` — checked by `_asegurar_visible`. A missing key means public, so existing tournaments keep publishing everything. Positions, calendar, goleadores and valla are always public by design. Hidden sections return 403 to the public and 200 to the owner/superadmin; the frontend catches the 403 and just omits the section.

### Plans and quota (`User.max_tournaments`)

The commercial lever. NULL means unlimited, which is how every existing account stays after the update; a number caps how many tournaments that organizer can own. `_asegurar_cupo_disponible` (in `tournament_routes.py`) counts `Tournament.owner_id == user.id` and returns 403 when the quota is spent — legacy tournaments (`owner_id IS NULL`) do not consume it. Only the superadmin can set it (`POST /auth/register`, `PUT /auth/users/{id}`); an organizer trying to raise their own gets a 403. `GET /auth/me` reports `max_tournaments` + `tournaments_count`, which is what paints the "1 de 2 campeonatos" badge and disables the create form.

### Team crests (`logo_url` as a data URI)

`Team.logo_url` takes either a link or **the image itself** as a `data:image/...;base64,` URI, which is what the panel sends when the organizer uploads one. It is stored in the DB rather than as a file on disk on purpose: the crest then travels with the backup, survives a move between SQLite and Postgres or a redeploy without a `/data` volume, and — the reason that decides it — loads into a canvas without CORS, which is what the acta and the PNG exports of standings, calendar and bracket do with it. `schemas.validar_imagen` is the gate: http(s) or a png/jpeg/webp/gif data URI, nothing else (`logo_url` ends up in an `<img src>`), capped at `MAX_IMAGEN` (400 000 chars). It runs on the way **in** (`TeamCreate`/`TeamUpdate`) and deliberately not on `TeamBase`, since `TeamResponse` inherits from it and old rows must stay readable. The frontend never sends a raw file: `utils/imagen.ts` (`escudoDesdeArchivo`) draws it into a canvas at 256 px and encodes webp (png where webp is unsupported), which lands a normal crest at 2-10 KB. Sending `logo_url: null` clears it.

### Bracket propagation (`services/bracket.py`)

A `WINNER_OF` / `LOSER_OF` slot used to be resolved **once**: the team went up and the slot was marked resolved for good, so when the referee corrected the score of a semifinal the team already in the final stayed there and there was no way to fix it from the app. `propagar_resultado(db, match)` now syncs every slot fed by that match with the result it has **right now** — and follows the cascade forward, because a new finalist can mean a new winner of the final. A match that stops being `finished` (corrected to live, or postponed) empties the slot it had filled: a blank box beats a team that won nothing. `_auto_resolve_winner_slots` (behind `POST /stages/{id}/resolve_position_slots`) does the same sweep over a whole stage, which is what repairs the tournaments left crooked by the old behaviour.

### How a knockout tie is decided (`services/bracket.py`)

What a slot points at is no longer forcibly one match, and the score alone no longer decides.

- **The penalty shootout** (`Match.home/away_penalties`) did not exist. The only way to record one was to load the score with the winner on top, so a 2-2 settled 4-3 was stored as 3-2: the acta printed a result that never happened. The shootout now has its own columns — a shootout penalty is not a goal, so it never reaches the table, the goalscorers or a tie's aggregate — and the match score stays as it ended.
- **Two-legged ties.** `Stage.config.two_legged` makes `seed_bracket` create two matches per crossing sharing a `tie_id`, told apart by `leg`, with home and away swapped on the second. Each leg carries its own slots, so correcting either one rewrites the bracket; the slots pointing forward reference leg 2, and `propagar_resultado` looks up slots by **every** match of the tie, so finishing the first leg also triggers the sweep. `Stage.config.away_goals` (off by default — UEFA dropped the rule in 2021) breaks an aggregate tie on goals scored away. The third-place match stays a single match.
- **The order of resolution** is the rulebook's: aggregate → away goals (if the stage turns them on) → the shootout of the deciding leg → the home team. That last resort is the old behaviour and is kept on purpose: there are loaded tournaments where the referee wrote the winner on top and there is no shootout to read.

`resolver_llave(db, match)` returns the winner, the loser, the aggregate and the **reason** (`global`, `gol_visitante`, `penales`, `marcador`, `localia`); `bracket_tree` ships it as `llave`, which is what lets the bracket say *«Pasa X 4-3 en penales»* instead of showing a draw and a team that advanced for no visible reason. The frontend never recomputes the winner of a tie from the score: `TournamentBracket` and the bracket share image read `llave.ganador_id`, and the captain's app reads the `my_penalties`/`rival_penalties` that `/captain/matches` carries, because an empty-looking draw that actually knocked their team out is exactly what they open the app to find out.

### Matches that are not played: postponed, W.O. and point sanctions

Three things the rulebook has and the app did not:

- **`MatchStatus.POSTPONED`** — it rained, the round moves. It does not count for the table (only `finished` accumulates), `detectar_conflictos` skips it entirely (a postponed match collides with no one and its missing date is the point), and giving it a new `scheduled_start` through `update_match_schedule` puts it back to `scheduled` — otherwise it would stay postponed forever, outside the table and outside the validator.
- **`Match.walkover`** (`home` / `away` / `both`) — who did not show up. The match stays `finished` **with** a score, so everything downstream keeps working, but it is on the record that it was not played. Sending no score fills in the one the discipline's rulebook fixes (`marcador_walkover` in `strategy.py`: 3-0 for football and its variants, 20-0 for basketball as in FIBA). `both` is 0-0 and `calculate_standings` counts it as a **loss for both**, not the draw a 0-0 would suggest. `walkover: null` clears it.
- **`TournamentTeam.points_adjustment`** (+ `_reason`) — the point sanction. Punishing a team used to mean touching its results, which is lying to the table; this adds points (negative to deduct) without touching a single match, and travels with its reason because a -3 with no explanation is what makes the organizer lose the argument. `PUT /tournaments/{tid}/teams/{team_id}/points_adjustment` (staff, own tournament, capped at ±100); `_ajustes_de_puntos` feeds it to `calculate_standings`, which applies it **before sorting** — a deduction that does not move the team is not a sanction — and leaves it on the row as `points_adjustment` so the table can show it.

### Tejo: the discipline that is not played against the clock

Everything else in the catalogue is a sport where the clock ends the match and the scoreboard moves one at a time. Tejo is neither, and that is what makes it a discipline of its own rather than a label:

- **It is played to 21 points, so there is no draw.** `TejoStrategy` is win/loss, and it is separate from `BasketballStrategy` for one number: FIBA gives the loser 1 point and the tejo leagues give 0. The table therefore hides the «E» column (`drawsPossible` in `sports.ts`) — a column of zeros with the air of a statistic is worse than no column.
- **The plays are worth different amounts.** The *mano* (the tejo closest to the bocín) 1, the *mecha* 3, the *embocinada* 6 and the *moñona* — mecha and bocín in the same throw — 9. They are declared in `scoreEvents` (front) and `PUNTOS_POR_EVENTO` (back), so the referee's panel paints one button per play **with its value printed on it** (nobody at the pitch remembers what an embocinada is worth), the scoreboard moves by that amount, correcting a play moves it by the difference, and the scorer table ranks by points. Every other discipline declares a single play worth 1 and behaves exactly as before.
- **There are no cards**: what is recorded is the line fault (`FALTA`), which does not accumulate in `services/disciplina.py`, so the suspension rulebook simply never fires for tejo.
- The W.O. is **21-0** and the defaults are 45 min + 10 of rest, which is how long it takes to pick the tejos up and replace the mechas.
- The panels that said *Goleadores* and *Valla menos vencida* now ask the discipline what they are called (`scorersLabel` / `defenseLabel`): a cajón of tejo has no goal to beat.

### The draw: pots, separations and bracket seeding

Pure chance over the whole list drops the four favourites into the same group with complete naturalness, and that breaks the tournament before it starts.

`POST /tournaments/{tid}/teams/shuffle_groups` now takes **`pots`** — the bombos, from the first to the last. Each pot is dealt one team per group before repeating, so the seeds come out separated and what is actually drawn is *which* group each one falls into. Teams in no pot go into a final implicit pot, which is what lets the organizer seed only the four top seeds (by last edition's table, say) and leave the rest to chance. It also takes **`keep_apart`**: teams from the same club or the same barrio that must not share a group. It is honoured where possible, and where it is not — three mutually exclusive teams and two groups has no solution — the response carries `avisos` and the draw still finishes, the same philosophy as the calendar validator: warn and let the organizer decide, never block. With no pots and no separations it is the shuffle of always.

On the bracket side, `_orden_siembra(size)` places the seeds in **bracket order** (`[1, 8, 4, 5, 2, 7, 3, 6]` for eight). Seeding by merit and then pairing crossing 1 with crossing 2 is what the tree did before, and it meant the winner of 1-8 met the winner of 2-7 in the semifinals: the top two seeds eliminated each other one round early and the whole seeding was decorative. `_evitar_reencuentros` then undoes any first-round pairing between two teams from the same group — standard in any cup — by swapping away teams between ties, and reports an `aviso` when no swap works.

### Building the bracket by hand (`components/CuadroBuilder.tsx`)

Defining the crossings used to be a row of dropdowns per tie — «grupo A» + «1» + vs + «grupo B» + «2» — a separate list for the byes, and three buttons (*sembrar*, *avanzar*, *resolver*) whose difference was visible nowhere. The organizer had to know from memory that a bracket of six needs two crossings and two byes, because the only way to find out was the server's 400, and at no point did they see the tree they were defining.

The tab (once *Avance*, now **Cuadro**) is a board. Three numbered steps — where the qualifiers come from, where the bracket is played (with a button that creates the stage if there is none), and the board — and inside the board the first-round ties are slots and the qualifiers are chips you drag. What that changes:

- **The tree is visible.** The ties are laid out in bracket order and grouped in pairs (the same `.bk-*` the public bracket uses), the pair that meets in the next round: that is what shows the 1st and 2nd seeds ending up in different halves, which is exactly what a list of crossings hides. A «Después» column names who enters each second-round match.
- **A bye is an empty slot**, not a parallel list: leaving one side without a team *is* passing directly, and the tie says so in words. Since the `plan` travels to the server, the bye waits in the tie where it was left.
- **The arithmetic is checked on screen.** The create button enables when the tree closes; while it does not, the screen says what is missing («la llave 3 está vacía», «al menos una llave tiene que tener dos equipos») instead of letting the server answer.
- **One create button.** A knockout destination goes to `seed_bracket`, anything else to `advance`. Those were two buttons doing different things without saying so.

The chips are *sources*, not teams: `1º Grupo A`, `Repescado 2` (the backend's `__best_thirds__`) or `Ganador de <partido>` (the play-in), with the team's name underneath once the groups resolve it. That is what lets the bracket be drawn **before** the groups finish and fill itself afterwards. «Ver todas las posiciones» opens the rest of the table for whoever wants to hand-pick a team that did not qualify.

Dragging uses `useArrastreEntreZonas` from `dnd.tsx` (pointer events, not the HTML5 drag API, so it works the same with a finger), with the same rule as the groups board: with a mouse you grab anywhere on the chip, with a finger only from the handle, so touch scrolling is not blocked. And **tapping is enough too**: tap a chip and then a slot does the same, because at the field it is used one-handed. The bench is one more zone, so dragging a chip out of the bracket returns it.

`sembradosPorMerito` + `cuadroPorMerito` fill the board in one go with the standard seeding (`ordenSiembra`, the same order as the backend's `_orden_siembra`), and `evitarReencuentros` undoes first-round crossings between two teams from the same group, exactly as the server does in its preview. Whatever it seeds can still be dragged: the seeding is a starting point, not a destination.

### Match sheet (`MatchLineup`)

The acta is signed at the field to leave a record of who was on the pitch, and it used to print the team's whole roster, which proves nothing. `MatchLineup` holds who played that match (`is_starter`, `is_captain`, and the `number` they wore that day, copied so a later change of jersey does not rewrite history). It is loaded per team — each delegate hands their list in when they arrive, never both at once — replacing whatever that team had; the other team's is untouched. A player who is not on the team's roster is rejected with their name, which is where eligibility control starts. Reading it is public (the acta circulates around the league); writing it takes the same `_asegurar_puede_dirigir` as loading the result, and the referee panel queues it offline like everything else in the field.

### Suspensions by accumulated cards (`services/disciplina.py`)

Three yellows are one match in almost any rulebook, and the question that matters on Saturday — *«¿quién no puede jugar mañana?»* — had no answer: the referee loaded the card and that was the end of it.

**It is off unless the organizer turns it on**, and that is a product decision, not a technical convenience: there are leagues that settle discipline in a committee and do not want the system marking anyone, and turning it on halfway through a tournament would change the rulebook with the ball rolling. Without `Tournament.discipline_config.enabled` none of this exists for that tournament — which is also how every tournament that already existed keeps behaving. The config carries the numbers because rulebooks differ: `yellow_limit` / `yellow_matches`, `red_matches`, `double_yellow_matches`, the optional blue accumulation, and `reset_stage_id`, which is the *«las amarillas se borran para la fase final»* rule.

Like the standings, **nothing is stored**: it is recomputed from the events, so a card the referee corrects on Sunday morning moves the suspension at once. The rules that took thinking: only cards from **finished** matches count (one from a match in play can still be corrected); a double yellow is charged as an expulsion and those two do **not** go back into the accumulation, since that would be charging them twice; and a suspension is served with the matches the team plays **after** the card — deliberately without looking at who was on the match sheet, because if the suspended player played anyway that is an *alineación indebida* for the organizer to settle, not something a counter should hide.

`GET /tournaments/{id}/discipline` returns `sanctions` (who cannot play and for how many matches) and `at_risk` (one card away — the warning a captain wants *before* the match, not after), and follows the same `sanciones` publish switch as the rest. It is painted in the public scoreboard, in the captain's app (*No pueden jugar*) and — where it actually stops an ineligible line-up — in the referee's match sheet, which marks the suspended player as they are being written in.

### Audit trail (`services/auditoria.py` + `core/log.py`)

A score is a column that gets overwritten, so «alguien me cambió un resultado» had no answer: not who, not when, not what it said before. Every write that can end in an argument — the score, a corrected event, the match sheet, the points sanction, a reschedule, a password reset, deleting a tournament — now leaves an `AuditLog` row with the actor, the previous value and a sentence written in Spanish at the moment of the change (nobody is going to reconstruct it from ids a month later). `diferencias(antes, despues)` keeps only the fields that changed, so the history is not a dump of twenty columns.

Two rules hold this module together: **it never breaks the operation it audits** (if the trail fails, the goal is still saved — the failure goes to the log and the request continues), and **it writes to both sides** (the DB answers from the panel, stdout survives the DB being lost or the commit never landing). `user_email` is a copy and `user_id` is not a foreign key on purpose: deleting an account must not delete the proof of what it did.

Read it from `GET /tournaments/{id}/audit` (staff + own tournament; the referee and the public get 403) and `GET /auth/audit` (superadmin, only what hangs from no tournament: account creation, resets, recovery requests). `core/log.py` is the other half — the backend used to write not one line of its own: now the startup says which DB it runs against and whether outgoing mail is configured, every login (and every failed login) is logged, and each audit entry doubles as a log line.

### Password recovery (`services/correo.py`)

Support resetting a password by hand works with twenty accounts and stops working with two hundred. `POST /auth/forgot_password` sends a link (`APP_BASE_URL/?reset=<token>`) and **answers exactly the same whether or not the account exists** — otherwise it would be a comfortable way to find out who has an account — with the send in a `BackgroundTask` so the response time does not give it away either. `POST /auth/reset_password_confirm` exchanges the token for a new password.

The token is `secrets.token_urlsafe(32)` and only its **SHA-256** is stored (`hash_token`): plain sha256 and not bcrypt because the server generates it with 256 bits of randomness, so there is no dictionary to try. It is single use, expires in `RESET_TOKEN_MINUTES`, asking for a new one invalidates the previous ones, and it clears `must_change_password` since the owner chose it. **With no `SMTP_HOST` nothing is sent and nothing fails**: the platform stays exactly as it was, with support resetting by hand.

### Notifications (`services/notifications.py`)

Captains have to find out when a match moves. `snapshot_partido(match)` is taken **before** the write, and `notificar_cambio_de_partido(db, match, antes)` compares it with the result: first time it gets a date → `partido_programado`; date changed → `partido_reprogramado` (the title says *aplazado* or *adelantado*, and the body carries both dates); only the court changed → `partido_cancha`. `notificar_estado_de_partido` covers `partido_en_vivo`, `partido_aplazado` (there is no new date yet, and for the captain the difference is whether they play on Sunday) and `partido_resultado`, whose body says who did not show up when the match was a W.O. Every aviso is written for the captains of **both** teams (`capitanes_de_equipos`), the helper never commits (the endpoint does), and it returns how many it created — that is where the `notifications` field of the bulk calendar response comes from. Adding push or WhatsApp means touching only this module.

### Calendar validation (`services/validacion_calendario.py`)

The auto-scheduler never overlaps its own slots, but the moment the organizer edits an hour by hand nothing stops two matches sharing a court. `detectar_conflictos(db, tournament)` re-reads the calendar and reports, split into `error` (impossible to play) and `aviso` (worth a look): `cancha_ocupada` (same court, overlapping times — including a match from **another** tournament on that court, named only if the caller may see it), `equipo_solapado`, `arbitro_ocupado`, `orden_de_llave` (a knockout match starting before the match that feeds it ends, via `StageSlot.source_match_id` — and a second leg scheduled before its own first leg, which that check cannot see because both legs hang off the same source), `equipo_sin_descanso` (gap below `min_rest_minutes`, defaulting to one match duration), `sin_fecha` and `sin_cancha`. **Postponed matches are dropped before anything is checked** (their own and other tournaments'): a suspended round must not fill the panel with errors, and a match without a date is exactly what postponed means. Exposed as `GET /tournaments/{id}/schedule_conflicts`; **it never blocks or fixes anything** — the organizer sometimes knows something the system doesn't, so the panel warns and they decide. A match's window is `scheduled_start` → `scheduled_end`, falling back to `match_duration` when the end is missing or stale; `update_match_schedule` now recomputes `scheduled_end` whenever the start moves, which is what keeps those windows honest.

### Qualification systems

`QUALIFICATION_PRESETS` (in `tournament_routes.py`, exposed by `GET /tournaments/qualification_presets`) names the common systems; `stage.config["preset"]` selects one and any explicit `qualifiers_per_group` / `best_thirds_count` in the config overrides it (`_reglas_clasificacion`). `stage.config["cross_tiebreakers"]` orders the comparison between teams from different groups (`cross_group_sort_key` in `strategy.py`; `PARTIDO_DIRECTO` is excluded because they never met). `GET /stages/{id}/bracket_preview` shows the crossings that the current configuration would produce — seeded by merit, best vs worst — without creating anything. In the panel (`StageConfig` in `AdminView.tsx`) that whole block — qualification system, cross-group tiebreakers and the preview — **only shows for a `group` stage**: with one table there are no groups to compare, so in a league, a swiss or a knockout those fields did nothing and the organizer filled them in anyway. Each stage type also carries a one-line description of what it is (`STAGE_TYPES[].pista`), because the dropdown offered four bare words, «Suizo» among them, and picking wrong only showed up when the fixture was generated.

### Stage-scoped statistics

`GET /{tournament_id}/player_stats`, `/team_stats` and `/fairplay` accept `stage_id` + `mode`: `from` (default — that stage and every later one, by `order_index`) or `only`. That is what backs the public "Cuentan desde" filter for goleadores, valla menos vencida and sanciones; with no `stage_id` they aggregate the whole tournament as before.

### Tiebreaker rules

`Tournament.tiebreaker_rules` is a JSON array applied in order by `services/strategy.py`. Supported keys: `PUNTOS`, `DIF_GOLES`, `GOLES_FAVOR`, `GOLES_CONTRA` (fewer is better), `FAIR_PLAY` (card penalty, fewer is better), `PARTIDO_DIRECTO` (head-to-head mini-table among tied teams). `GET /api/v1/tournaments/tiebreaker_options` returns the labeled set.

### Frontend (`frontend/src/`)

React 18 + Vite + TypeScript, built as a **PWA** (`vite-plugin-pwa` + Workbox). Stack: **react-redux** (only `authSlice` — token, role, user id, mirrored to `localStorage`), **Tailwind CSS**, **Framer Motion**, **jsPDF**, **DOMPurify**, **qrcode**.

#### Visual system («Hive Arena»)

The look lives in three files and everything else inherits it: **`tailwind.config.js`** (tokens), **`src/index.css`** (base, textures and animations) and **`src/components/ui.tsx`** (primitives). The token *names* never change — `secondary` is still the action accent — so retuning the palette moves the four views at once.

Two ideas hold it together. **The hexagon is the shape of the house**: the brand is a hive, so `.bg-hive` tiles a honeycomb behind the heroes and `.clip-hex` crops emblems, crests, leader positions and empty-state icons. **The accent is voltage**: lime `#C7FF3F` on near-black ink `#070910`, reserved for what can be done and what is happening now, with orange `#FF6A3D` for urgency (live, postponed, W.O.). Each discipline also carries its own colour — `volt`, `ice`, `plasma`, `flare`, `ember` — so a football tournament and a tejo tournament do not look alike.

Type is **Archivo**, variable and with a width axis: `.headline` sets `wdth 120` + uppercase for section titles, which is what gives it the broadcast-graphics feel; `.tnum` fixes figure width so a scoreboard does not dance. Utilities worth knowing: `.btn-sheen` (a light sweep across an action button), `.hover-lift`, `.glass` + `.edge-glow` (the fixed top bars), `.live-dot` / `.live-ring`, `.noise`, `.text-volt-gradient`. `@media (prefers-reduced-motion: reduce)` turns all of it off.

New primitives in `ui.tsx`: `HiveMark` (the hexagonal emblem), `Stat` (a KPI tile), `SectionTitle` and `Eyebrow` with its accent tick.

`App.tsx` routes by role: `referee` → `RefereeView`, `captain` → `CaptainView`, anything else → `AdminView`; without a token it shows `LandingView`/`PublicView`. The views are large and self-contained: `AdminView.tsx` holds every admin tab (torneos, equipos, fases, calendario, jugadas, config) plus `DashboardView`, `VenuesPanel` and `UsersPanel`; `PublicView.tsx` is the whole public scoreboard. The *cuadro* tab lives apart, in `CuadroBuilder.tsx` — see *Building the bracket by hand* below.

- **`CaptainView.tsx`** is the captain's whole app: team picker (if they run more than one), a "próximo partido" card with date, court and venue, calendar (upcoming / played), a team tab with record, form, position per stage and per-player stats, and a **Mejores jugadas** tab with the clips of their matches, framed by the same `JugadaPlayer`. It only calls `/captain/*`.
- **`RefereeView.tsx`**'s "Registro en vivo" corrects and deletes what was already loaded: the pencil turns the row into an inline editor (equipo, tipo, jugador, minuto — and "sale" when it is a CAMBIO) and the trash asks for a second tap before deleting, because in the field the thumb wanders. The controls only appear for a match the user can actually direct (`role !== 'referee' || match.referee_id === userId`), mirroring the backend. **The score is not derived from the events** — the referee also moves it by hand — so correcting or deleting a GOL moves the counter the same way the "Gol" button moved it (`ajustarMarcador`), and the aviso says to save. The **"Penales"** button opens the shootout panel: two numbers that do not touch the score, because a shootout penalty is not a goal — before this the only way to record one was writing the winner on top and the acta printed a match that never happened. The **"No se jugó"** button opens the panel for the match that does not happen: *Aplazar*, or *No llegó X* for either team or neither (W.O., with the score `marcadorWalkover` fixes so the number is right even with no signal). The **"Planilla del partido"** card under the board is where the referee marks who played: a checkbox per rostered player, a T/S toggle for titular/suplente, a star for the captain, "todos titulares", and one save per team — the same `readOnly` gate as the rest, so a referee who is not on that match sees it but cannot touch it.
- **`NotificationsBell.tsx`** lives in the `Layout` header for every role: unread badge polled every 60 s, dropdown with the avisos, click marks read.
- **`UsersPanel.tsx`** is the account panel for superadmin *and* organizer — the same screen, scoped by what the backend returns. It creates accounts, edits role/quota/name, toggles active, and shows the temp password from a reset once, with a copy button. At the bottom, for the superadmin only, *Actividad de cuentas* reads `/auth/audit`: who was created, whose password was reset and who asked to recover theirs.
- **`LoginView.tsx`** is three screens in one (`Modo`): sign in, *¿Perdiste el acceso?* (asks for the email and always answers the same thing) and *Elige tu contraseña*, which is what `?reset=<token>` opens. `App.tsx` reads that token and **wipes it from the address bar** with `history.replaceState` as soon as it does: it is a credential and has no business staying in the browser history.
- `HistorialTab` (in `AdminView.tsx`) is the tournament's audit trail: one line per change with the icon of its kind, the actor and the date, and clicking it opens what it said before → what it says now. The filter chips are built from what is actually there, so a tournament with no sanctions does not show an empty *Sanciones* filter.
- `Layout.tsx` opens the password modal by itself and refuses to close it while `auth.mustChangePassword` is set (the flag comes from the login response and is cleared by `passwordChanged`).
- `ValidacionCalendario` (in `AdminView.tsx`) sits on top of the calendar tab: it re-checks after every manual edit, auto-schedule or draw, lists each conflict with its reason, and marks the offending rows with a red (error) or amber (aviso) left border.

- **`src/utils/imagen.ts`** turns the file the organizer picks into a small crest (256 px, webp with a png fallback) before anything leaves the browser — see *Team crests* above. `TeamLogo` (in `AdminView.tsx`, next to `TeamColors`) is the control: preview, upload, and an × to remove.
- **`src/sports.ts`** is the single source of truth for disciplines: label, icon, accent colour and gradient, score unit, **the plays that move the scoreboard** (`scoreEvents`, each with the points it is worth), the referee's discipline buttons, the public table's card columns, whether a draw is even possible (`drawsPossible`), what the scorer and defence panels are called (`scorersLabel` / `defenseLabel`) and the W.O. score (`walkoverScore` / `marcadorWalkover`, the same the backend applies). Adding a sport = one entry here plus the `SportType` value in the backend. Never re-introduce `sport_type === 'micro'` checks in components — use `sportOf()` / `hasBlueCard()` / `puntosDelEvento()`.
- **`src/theme.ts`** holds the same tokens as `tailwind.config.js` as raw hex, for where Tailwind cannot reach: the recharts series, the canvas of the share images and the QR. Two files, one system. The PDF acta deliberately does **not** use it — it prints on white paper in navy ink.
- **`src/utils/partido.ts`** holds the labels of a match that is not played (`ESTADO_LABEL` with *Aplazado*, `woLabel`, `woDetalle`) and of the knockout tie (`penalesLabel`, `legLabel`, `resumenLlave` — the sentence that turns a 2-2 into *«Pasa X en penales»*). It exists because those strings are painted by the public scoreboard, the organizer's calendar, the referee panel, the bracket and the captain's app: a raw `postponed` on screen is one error visible to the public in five places at once.
- **`src/utils/socialImage.ts`** draws the share images on a canvas (resultado, próximo partido, posiciones, calendario, cuadros de estadísticas and bracket). **Long lists are never truncated**: `makeStandingsImage`, `makeCalendarImage` and `makeStatsImage` return a `Blob[]` — one image per page, split evenly by `paginar()` so 22 matches go 8/7/7 and not 9/9/4, with the same row height on every page and a "2 / 3" chip under the wordmark — and `shareImages` / `downloadImages` post them as a carousel or save them all. The index handed to `TableCol.cell(r, i)` is the global one, so the "#" column keeps counting 11, 12, 13 on the second image. Sponsors (max 5) are redrawn on every page. **The image goes out in two palettes.** The module was wired to the dark system, and the image is not read where the app is read: it lands in a WhatsApp thread or an Instagram story, where the background is whoever receives it. A near-black square in a light thread reads as a hole, the league that prints the calendar to pin it at the court spends a cartridge on the background, and the tournament whose own brand is light has no way to publish in it. So the five makers take a `Paleta` as their last argument — `PALETA_OSCURA` by default, so nothing that is already being shared changes — and the organizer picks it in the share modal of the public scoreboard (*Oscuro* / *Claro*, remembered in `ch_tono_imagen`, because that screen has nine share buttons and whoever publishes in light publishes everything in light); the same choice drives the table's direct PNG and the bracket PDF, which are the same image through another door. The dark variant is read from `theme.ts` rather than repeating the hexes — its only hex of its own is `fondoAlto`, the far stop of a gradient painted nowhere else — and the light one lives here and not in `theme.ts` on purpose: that file is the app's system and the app is dark by design, while these tones exist only for what is exported. **Two token pairs look redundant and are not**: what is *read* against the background (`acento`, `urgencia`) is separate from what is a brand *fill* (`acentoRelleno`, `urgenciaRelleno`), because the lime on white has 1.3 of contrast — as text it does not exist — but as a fill with dark ink on it it works in both, and that is exactly what must survive the switch. The faint tones are **not** fields: `velo()` derives them from the palette, since an alternating row or a separator is ink at low alpha *over* the gradient, and opaque hexes there would cover the gradient, which is half the air the image has. **The crest that disappears** is why `placaPara()` decides against the active palette and not against a fixed darkness threshold. A black crest on the brand background simply does not exist, and it is a common case — `utils/imagen.ts` encodes webp precisely to keep transparency, so a dark-ink logo arrives whole and is drawn over nothing — but in light the problem is the same one inverted: the one that vanishes is the white logo. So the question is not «¿es oscuro?» but «¿se parece al fondo?»: a crest whose luminance is within 55 of the background's gets a plate of that palette's `texto`, which is by construction the pole opposite its `fondo`. The black crest is rescued on dark, the white — and the lime one — on light. It is not given to everyone, because a plate behind a colored crest turns it into a box nobody asked for; the acta in `pdf.ts` (`escudo`) does give it to everyone, white and with a border, because there the background is paper and there is no contrast to borrow. What is measured is the perceived luminance of the **opaque** pixels only (counting the transparent background would make any airy logo read as dark), and what is cached per image is that measurement and not the decision, which depends on the palette.
- **`src/components/JugadasPanel.tsx`** is the upload/manage panel, shared by the organizer (tournament tab, every match) and the referee (their own match, locked). **`JugadaPlayer.tsx`** is the framed player plus `ChipJugada`, the one chip used by the panel, the reel and the player. **`src/utils/clip.ts`** reads the picked file: unlike `imagen.ts` it does **not** transform the video (re-encoding in the browser takes longer than uploading and loses quality) — it measures it and pulls a poster frame.
- **`src/utils/pdf.ts`** holds the **acta del partido** (`exportMatchReportPDF`), the document the organizer prints, signs at the field and hands to the club — see *Acta del partido* below. Same file: the standings PDF and `exportImagePDF` (a ready PNG, e.g. the bracket, dropped into a page).
- **`src/services/api.ts`** wraps every endpoint and handles the offline outbox (`services/offline.ts`) so referees can load results without connectivity. An event created without signal only lives in the queue, so its optimistic id **is** its outbox id (`tmp_…`): correcting it rewrites that pending POST (`patchQueuedEvent`) and deleting it cancels the send (`dropQueuedEvent`), instead of firing a PUT/DELETE for an id the server never saw. `StatScope` (`{stageId, mode}`) is what powers the "Cuentan desde" filter.
- Sections the organizer hid return 403; the frontend catches it and omits the section rather than showing an empty table.

### Best plays: the clip inside its frame (`api/highlight_routes.py`)

The organizer records the goal on their phone and sends it by WhatsApp, where two days later nobody can find it. `MatchHighlight` pins the clip to the match and to the play it was, and the public scoreboard grows a **Mejores jugadas** tab per tournament.

**The video does not live in the database.** The team crest does, as a data URI, and on purpose (2-10 KB, it travels with the backup, it loads into a canvas without CORS). A twenty-second clip weighs megabytes: the file goes to disk under `MEDIA_ROOT` and the row keeps the record plus `media_path`, which is what lets the file be deleted with the play instead of leaving orphans on disk. `storage` says where the video comes from and there are three real cases: `local` (uploaded here), `link` (the league already publishes on YouTube or Instagram — pasting the URL costs no storage and covers whoever will not pay for it) and the optional `contentful` mirror. A **poster frame** rides along as a small data URI like the crests, so the reel's grid paints without downloading a single video.

**The play types are tied to the discipline**, which is the point and not a detail: a tejo court has no *atajada*, it has a *moñona*. `JUGADAS_POR_DEPORTE` + `validar_jugada` (in `services/strategy.py`, where the other per-discipline facts already live) hold the catalogue, and `highlightPlays` in `sports.ts` is its front-end half with icon and tone. A play the discipline does not have is a 400 **naming the ones that do exist** — the organizer is uploading from the stands and a bare "not valid" makes them guess. `OTRA` exists in every discipline because the clip that is none of the above (the celebration, the crowd) always shows up, and rejecting it is worse than a generic bucket.

**Who uploads is the same split as who loads the result**: the owner of the tournament and `Match.referee_id`, through `_asegurar_puede_cargar`. The referee is the one standing on the pitch with the video in their pocket, and asking them to forward it to the organizer is how clips get lost. Moving a play to another match requires permission over the *destination* match too, not just the origin.

**What the captain sees** is their team's plays *and* the plays of the matches they played — the rival's goal included, because the reel of a match is the story of the match and cutting it to one side leaves it telling half; `is_mine` marks the difference so the screen can say *Del rival* instead of showing a strange crest with no explanation. Their endpoint **filters** a tournament whose `jugadas` switch is off rather than answering 403 like the per-tournament reel does: that query crosses every tournament they captain, and one organizer's switch must not blank the rest.

**The clip is the only thing in the referee's panel that needs signal.** Everything else queues offline, so the referee assumes they can work without it; a 20 MB clip in the browser's storage is how the whole outbox gets corrupted, so `isQueueable` (a whitelist) leaves this route out and the panel says so before the clip is even picked.

`services/media.py` guards the three things that matter because the file is served back from the app's own origin: **the server picks the name** (a uuid, never the client's), **the extension decides the Content-Type** (a .html uploaded as a video would be a stored XSS), and **the first bytes are read** (a renamed .exe passes any extension check). The size cap is enforced *while writing*, not after — checking at the end means the 2 GB file is already on disk.

### The frame: one canvas, two uses (`utils/marcoJugada.ts`)

The clip is not read where the app is read: it lands in a WhatsApp thread or an Instagram story. A CSS overlay dies the moment someone downloads the video — exactly when the sponsor needed to be on it. So the frame is drawn on a **canvas** and `utils/exportarJugada.ts` burns it into a new file with `MediaRecorder`, mixing the element's audio in through an `AudioContext` (a goal without the crowd is half the play). It is the same reasoning already written down for `socialImage.ts`, applied to video.

That is also why the in-app player (`JugadaPlayer.tsx`) paints that same canvas instead of a `<video>` with divs on top: one renderer rather than two designs that drift apart, and the preview is **literally** the file that will be exported — which is what the organizer is checking when they look at where the sponsor's logo ended up.

The layout is measured in units of the **height** (`u = alto / 100`), because half the clips arrive vertical from a phone and a frame in fixed pixels is tiny at 1080×1920 and huge at 640×360. It degrades all the way down: no logo → the campeonato's initial inside the hexagon; no sponsors → no bottom band; no title → the player's name takes its place.

Two limits are stated on screen rather than hidden: a **linked** clip cannot be framed (the browser forbids reading another domain's video into a canvas, which `motivoSinExportar()` explains), and the export **records in real time**, so a 15-second clip takes 15 seconds — hence the progress callback, since without it the page looks frozen.

`mediaUrl()` (in `services/api.ts`) anchors the backend's relative `/api/v1/media/…` to the API's origin. In the combined image the frontend and the API share an origin and the relative path resolves on its own; with the backend on another host the browser resolves it against the **page**, and the SPA server answers its own index.html with a 200 — the `<video>` gets HTML where it expected video and fails with an error that explains nothing.

### Contentful (optional, off by default)

`CONTENTFUL_ENABLED` is false and that is a product decision: a neighbourhood league has no reason to pay for a CDN to publish Sunday's goal, and whoever does have one gains that the video is served from Contentful's network instead of the server's disk. Unconfigured it does not upload and **does not fail**, the same rule as `services/correo.py`, and it talks to the Content Management API through stdlib `urllib` for the same reason that one uses `smtplib`: no new dependency.

Uploading an asset is five round trips, not one, because the video processing is asynchronous (upload → asset → process → poll for the URL → publish). That is why the mirror runs in a `BackgroundTask` and not inside the request: the organizer who just uploaded 30 MB from the stands cannot wait for someone else's CDN. `POST /highlights/{id}/mirror` retries one by hand, because otherwise a failed mirror would mean deleting the play and uploading the video again.

### Acta del partido (`src/utils/pdf.ts`)

`exportMatchReportPDF(match, events, playerName, opts)` builds an A4 document, not a data dump: navy header with the tournament logo, the discipline and an acta code derived from the match id (`ACT-XXXXXX`), a scoreboard card with both crests, the status pill and a four-cell strip (fecha/hora, sede/cancha, fase, árbitro), then the planillas — goles, disciplina (the sanción cell is painted with the card's own colour), sustituciones and a per-team summary whose columns come from `sportOf(sport_type).events`, never from an `if` per sport — the planteles side by side with dorsal, documento, goles and sanciones — **the match sheet when there is one**: only who played, split into TITULARES and SUPLENTES with the captain marked `(C)`, since that is what the signature is attesting to; without a sheet it falls back to the full roster as before — an elastic *Observaciones* box that stretches to fill whatever is left, and the **firmas**: three boxes (delegado local, árbitro, delegado visitante) pinned to the bottom of the last page with a ruled line and a `C.C.` line. Under them a dark strip with a **QR to the public scoreboard** (`/?t=<tournament_id>`), because the printed acta circulates around the league and is the cheapest advertising there is.

It is `async` (crests and QR), and everything optional degrades: a logo whose server denies CORS or takes over 4 s is dropped and the team shows its initials over its uniform colours; without rosters the planteles say so; the *Parcial* column only appears when the goals loaded add up to the final score, since the referee also moves the scoreboard by hand. A match that is not `finished` gets a diagonal **PROVISIONAL / EN JUEGO / APLAZADO** watermark, which is also what makes the empty acta of a scheduled match a useful thing to print and fill in by hand; a W.O. is finished but stamped **NO JUGADO**, and the line under the score reads `GANA X POR W.O.`; a draw settled from the spot reads `GANA X EN PENALES 4-3` (the score itself stays 2-2) and the status pill says `IDA` or `VUELTA` when the match is one leg of a tie — that is what explains a 3-0 to whoever reads the acta weeks later. Images are embedded with `'FAST'` compression and capped at 360 px — a single logo took the file from 77 kB to 750 kB, and it is downloaded from the field on mobile data. Both the referee (match panel) and the organizer (each row of the calendar tab) can download it.

### Auth flow

`POST /api/v1/auth/login` (form-encoded) returns a JWT plus role and user id. The frontend stores them and routes by role; every subsequent request sends `Authorization: Bearer <token>`. A 401 on any call clears the session and reloads.
